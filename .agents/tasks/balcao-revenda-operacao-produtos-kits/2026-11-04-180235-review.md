# Produtos (R3) e Composição de custo (R4): lista por plataforma e editor de kit

As duas FEATs entregam a lista de Produtos (R3.8) com pills de estado, coluna "Custo un.", "N vendido(s)" e ✎ nas abelinhas, e constroem a Composição de custo (R4) do zero: lista com uma coluna por plataforma e um editor em painel lateral largo com itens do kit, custos adicionais, preço base/metas, resumo fixo e a tabela "Resultado por plataforma" que recalcula ao digitar. O domínio (`calcularKit`, `taxas`, `abelinhas`) e a feature Pedidos não foram tocados; `flutter analyze` está limpo e os 54 testes passam.

Watch for: a contagem de "vendidos" do kit (confirmed) nunca inclui os pedidos concluídos — o provider carrega pedidos sem itens, então a pill "Meta" só reflete os vendidos iniciais, contrariando R4.7 e o protótipo. O preço "Sugerido" (confirmed) soma sempre o desconto/cupom base e ignora o override por plataforma, divergindo de §6.3 e do protótipo.

**Verdict**: NEEDS_CHANGES

## High-level view

A lista de Produtos ficou fiel ao R3.8: pills `inativo`/`código repetido`, coluna `Custo un.` com fornecedor, estoque com `N vendido(s)` abaixo e ✎ nas abelinhas que reabre o editor. O editor de produto e os cálculos de abelinhas não foram mexidos, então o aviso de impacto (§6.7) segue intacto. O contador de vendidos por produto resolve o N+1 chamando `obterComItens` por pedido concluído — funciona, mas é justamente o padrão que a Composição deixou de aplicar.

A Composição carrega plataformas, kits, produtos e faixas por `when` aninhado e monta uma `ResponsiveList` com limiar 990, virando cartões em tela estreita (sem rolagem horizontal). Cada plataforma é uma coluna com lucro colorido e "cliente paga · margem".

O editor de kit reconstrói um `ProdutoVenda` em memória a cada `setState` e chama `calcularKit` por plataforma, o que faz a tabela recalcular ao digitar sem perder foco; os overrides por célula são mantidos em controllers nomeados por `platId_campo`. O resumo fixo e o "Melhor resultado" derivam do mesmo kit em memória.

O ponto que quebra o comportamento esperado é a origem dos pedidos: o `pedidosProvider` usa `PedidoRepository.listar`, que devolve pedidos sem itens, e `_vendidosEmPedidos` depende de `pedido.itens`. O resultado é que vendas registradas nunca contam para a meta do kit. Em menor escala, o preço sugerido usa desconto/cupom base mesmo quando a plataforma sobrescreve esses valores.

## "Vendidos" do kit não conta pedidos concluídos

A meta por plataforma (`R4.7`) é `vendidos iniciais + unidades do kit em pedidos não cancelados daquela plataforma`. No protótipo, `kitVendidos(k,pid)` soma `vendidosIni[pid]` com as linhas de kit dos pedidos ativos da plataforma.

Na implementação, `calcularKit` delega essa soma a `_vendidosEmPedidos`, que percorre `pedido.itens`:

```dart
for (final pedido in pedidos) {
  if (pedido.plataformaId != plataforma.id) continue;
  if (pedido.situacao != SituacaoPedido.concluido) continue;
  for (final item in pedido.itens) { ... }
}
```

Mas os `pedidos` vêm de `pedidosProvider`, que chama `PedidoRepository.listar`:

```dart
Future<List<Pedido>> listar(String empresaId) async {
  final linhas = await _client.from('pedidos').select()...;
  return linhas.map(Pedido.fromJson).toList(); // itens = [] (default)
}
```

`listar` não carrega `pedidos_itens` — os itens só são buscados em `obterComItens`. Como `pedido.itens` é sempre vazio nesse caminho, `_vendidosEmPedidos` retorna 0 e o total de vendidos fica preso em `vendidosIniciais`. A pill "Meta" (`vendidos/metaQtd`) e o verde de atingimento ficam errados assim que houver qualquer pedido concluído. A própria FEAT-001 já resolveu esse N+1 em `vendidosPorProdutoProvider` chamando `obterComItens` por pedido concluído; a Composição não aplicou o mesmo. Correção: carregar os pedidos concluídos com itens (ou adicionar um método de lote no repositório).

## Preço "Sugerido" usa desconto/cupom base, não o override

`§6.3` define que `preco/desconto/cupom = override da plataforma se preenchido, senão base`, e o protótipo calcula `sugerido = precoParaMargem(...) + pr.desconto + pr.cupom` com `pr = kitPreco(k,pid)` (o registro efetivo da plataforma).

A implementação usa só os valores base:

```dart
Decimal? _sugerido(List<FaixaTaxa> faixas, Decimal investimento) {
  if (_margemAlvo >= Decimal.fromInt(100)) return null;
  final base = precoParaMargem(faixas, investimento, _margemAlvo);
  return base + _desconto + _cupom; // ignora _precos[platId]
}
```

Numa plataforma que sobrescreve desconto ou cupom, o botão "Sugerido" aplica um preço que não produz a margem alvo (o cliente paga calculado com o override difere do usado para montar o sugerido). O impacto é restrito às plataformas com override de desconto/cupom, mas é uma divergência rastreável do protótipo. Correção: usar `_precos[platId]?.desconto ?? _desconto` e `_precos[platId]?.cupom ?? _cupom`.

## Produtos (R3.8): o que ficou fiel

A tabela monta as colunas `Produto` / `Custo un.` / `Abelinhas` / `Estoque`, com os pills `inativo` e `código repetido` (via `codigosRepetidosProvider`), fornecedor sob o custo, `N vendido(s)` sob o estoque e o ✎ que chama a mesma ação de edição. `codigosRepetidosProvider` deriva de `produtosProvider` e marca códigos que aparecem em mais de um produto. O editor de produto, o quadro de abelinhas e o controller não foram alterados, preservando R3.1–R3.6 e o aviso de impacto de §6.7.

`vendidosPorProdutoProvider` carrega cada pedido concluído com `obterComItens` e soma itens avulsos e itens de kit (expandindo `ProdutoVendaItem.quantidade × quantidade do kit`). É um N+1 por pedido, mas correto — e é o padrão que a Composição deveria ter reaproveitado.

## Composição: lista e recálculo do editor

A `ResponsiveList` com `limiarCartao: 990` gera uma coluna por plataforma (lucro colorido + "cliente paga · margem") e vira cartões abaixo do limiar, sem rolagem horizontal (R4.8/§7.4). O editor mantém os overrides de preço/desconto/cupom em `TextEditingController` nomeados por `platId_campo` e, a cada `onChanged`, atualiza `_precos[platId]` e chama `setState`, que reconstrói o `ProdutoVenda` em memória (`_montarKit`) e reexecuta `calcularKit` por plataforma. Como o lookup em `calcularKit` é `kit.precosPorPlataforma[plataforma.id]` e `_precosLimpos` chaveia por `platId`, a tabela recalcula ao digitar preservando o foco. O botão "Sugerido" grava o valor no controller e em `_precos` (ressalva na seção acima), e `_precosLimpos` descarta overrides vazios ao salvar.

## Raiz das pages e escopo

Tanto `ProdutosPage` quanto `ComposicaoPage` têm `Column` na raiz (o scroll fica no AppShell). O domínio, os cálculos e a feature Pedidos não aparecem nos dois commits; `flutter analyze` retorna "No issues found!" e `flutter test` passa os 54 testes.
