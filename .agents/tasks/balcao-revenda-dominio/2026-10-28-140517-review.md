# Camada de domínio do Balcão Revenda: entidades freezed + cálculos puros (§6)

As entidades freezed em `lib/domain/entidades/` espelham o schema de `supabase/migrations/0001_schema.sql`, com um `DecimalConverter` central que serializa `numeric` como `Decimal` (aceitando String e num do PostgREST, gravando String para preservar precisão). Os cálculos em `lib/domain/calculos/` são funções puras (só `dart:core` + `package:decimal` + entidades) que implementam as fórmulas do design.md §6 (taxa/preço mínimo, kit, pedido, abelinhas, caixa, painel). Todos os vetores numéricos do §6 estão cobertos por testes com tolerância 0,005 em R$ e os valores de exibição de 1 casa (percentuais, ROAS) com tolerância de arredondamento documentada.

Watch for: a divergência de nomenclatura da tabela de produtos — o schema SQL chama `produto_online`, enquanto o design.md §2 a resume como `produtos` (confirmed; não afeta a camada de domínio, pois entidades não codificam nome de tabela, mas o repositório da próxima fase precisa usar `produto_online`).

**Verdict**: APPROVED

## High-level view

As entidades cobrem todas as tabelas do §3 com `Decimal` para dinheiro/percentual/abelinhas e `@JsonKey(name:)` para o snake_case do banco; `itens`/`precosPorPlataforma`/`rateio` ficam fora do JSON da linha (montados pelo repositório), o que está correto para agregados carregados separadamente. O `DecimalConverter` lida com as duas formas que o PostgREST usa para `numeric` e evita passar por `double`.

Os cálculos seguem o §6 ao pé da letra, inclusive os detalhes sensíveis: `metaQtd` do kit usa o lucro **exibido** (arredondado a 2 casas) antes do `ceil`, que é o único caminho que fecha o vetor do Mercado Livre (299); margem é `lucro/líquido` no kit, `lucro/faturamento` no painel e `lucro/precoVenda` no pedido, cada um conforme sua seção. A divisão usa escala interna ampla e só arredonda na exibição, respeitando a regra de dinheiro do projeto.

A cobertura de teste bate com os vetores do §6.1 a §6.8, incluindo os 99 produtos reais lidos de `assets/seed/dados-iniciais.json` para as análises de abelinhas. `flutter analyze` está limpo, `flutter test` passa 45 testes, e `build_runner` gera sem erro.

### Entidades espelham o schema e as regras de dinheiro

Cada entidade corresponde a uma tabela do §2/§3. Campos monetários, percentuais e abelinhas são `Decimal` com `@DecimalConverter()`/`@DecimalNullableConverter()`, nunca `double` — alinhado com `numeric(12,2)`/`numeric(6,2)` e com a regra do projeto. Os nomes Dart em camelCase recebem `@JsonKey(name: 'snake_case')` quando divergem (`empresa_id`, `meta_lucro`, `fatia_roas`, `abelinhas_manual`, etc.), e nulos semânticos do schema são preservados: `Produto.abelinhasManual` null = regra, `FaixaTaxa.precoAte` null = sem limite, `PrecoPlataforma.preco/desconto/cupom` null = usa base.

`ProdutoVenda.itens`/`precosPorPlataforma`, `Pedido.itens` e `Saque.rateio` são marcados `includeFromJson/includeToJson: false` — não vêm na linha da tabela e são compostos pelo repositório. É a modelagem correta para agregados cujas coleções moram em tabelas-filhas.

O `DecimalConverter` aceita `String` ("12.50"), `int` (0) e `num` (12.5) na leitura e grava `Decimal.toString()`, evitando o caminho por `double`. O round-trip é testado com `numeric` vindo como String (formato PostgREST) e como num.

### Cálculos puros seguindo o §6

Nenhum arquivo em `lib/domain/calculos/` importa Flutter ou Supabase (verificado por busca); as dependências são `dart:core`, `package:decimal`, `freezed_annotation` (anotação de code-gen dos tipos de resultado) e as entidades. A extensão `CalculoDecimal.dividir` converte o `Rational` da divisão de volta a `Decimal` com escala interna de 20 casas e só arredonda na exibição (`arred2`), conforme a diretriz "arredondar só para exibir".

Três detalhes do §6 que são fáceis de errar e aqui estão corretos:

```
metaQtd = ceil(metaLucro / lucroExibido)   // lucroExibido = lucro.arred2()
```

O vetor do Batom no Mercado Livre (meta 299) só fecha usando o lucro arredondado a 2 casas antes do `ceil`; usar o lucro bruto daria 298. O código faz exatamente isso em `produto_venda.dart`.

As três definições de margem convivem sem se confundir: `lucro/liquido` no kit (`ResultadoKit`), `lucro/faturamento` no painel (`KpisPainel`), `lucro/precoVenda` no pedido (`ResultadoPedido`) — cada uma na função da sua seção.

`precoMinimo`/`precoParaMargem` iteram as faixas ordenadas (sem limite por último), validando `p > limite anterior` e `(ate == null || p <= ate)`, com o fallback pela primeira faixa quando nenhum candidato é válido — igual ao §6.2.

### Cobertura dos vetores com tolerância correta

Os valores em R$ são comparados por `esperaValor` com tolerância 0,005 (design.md §11). Os valores que o §6 apresenta já arredondados para 1 casa — percentuais de margem/ROI e o ROAS ≈ 51,8 — usam `esperaPct`/`esperaUmaCasa` com tolerância de exibição de 0,051 (meia casa). Isso é apropriado: o §6.5 mostra margem 40,1% que vem de 88,33/220 = 40,15%, um valor de borda; compará-lo com 0,005 em pontos seria comparar contra um número que a própria especificação só expressa arredondado. Os valores monetários subjacentes continuam sob a tolerância estrita.

### Verificação

`flutter analyze`: limpo ("No issues found"). `flutter test`: 45 passam (13 de baseline em `test/core/format` + entidades + todos os vetores §6). `dart run build_runner build --delete-conflicting-outputs`: conclui sem erro, gera os `.freezed.dart`/`.g.dart`.

### Nomenclatura da tabela de produtos

O schema SQL cria `public.produto_online` (com `unique(empresa_id, codigo)`), e os FKs `produtos_venda_itens.produto_id` e `pedidos_itens.produto_id` apontam para ela. O design.md §2 resume a mesma tabela como `produtos`. A camada de domínio não é afetada — entidades não carregam nome de tabela — e os doc-comments de `Produto` já citam `produto_online` corretamente. Fica como aviso para a fase de repositórios: as queries devem usar `produto_online`.
